FrameSpike 帧刺

v0.4.0

Minecraft 1.8.9 帧时间尖峰与卡顿分析 mod

Trusler · Forge 11.15.1 + ichor · Zulu 17 · 纯 coremod，零外部依赖

不猜硬件、不猜驱动。在主线程冻住的那一刻抓调用栈，把「卡了多久」和「卡在哪」同时写进日志和聊天栏。

简介

客户端卡顿通常有三种归因：GC、网络、渲染。但这个环境里三样都不是 —— -XX:+DisableAttachMechanism 封掉了 jstack / jcmd / JFR，服务端 spark 又只能给出时间窗总量、 没有单帧时间戳。FrameSpike 补的就是这一段：从 JVM 内部自采，抓单次冻结的栈和真实时长。

它只做三件事：

  1. 在 7 个每帧必经的方法入口注入检查点（约 20ns / 次）
  2. 发现主线程超过阈值没推进，就抓一次栈，并记录帧内时间线
  3. 等下一个检查点到来时结算真实时长，归好原因，写日志、可选推聊天

功能

  • 停顿取证：调用栈 + 帧内时间线（哪一步推进到哪）+ 真实时长分档
  • 原因归类：按栈顶前 6 帧归成一句简写 —— 写文件 / 类加载-remap / 窗口合成 / GL 驱动 / 音效 / 字体缓存 / 小地图 / OptiFine / 网络
  • 游戏内指令：14 个子命令，Tab 补全，全部可热改，不用重启
  • 聊天播报：卡顿时推一行 [FS] 312ms 写文件 FileOutputStream.writeBytes:0（三道闸防刷屏）
  • 全线程 CPU 表：用 ThreadMXBean.getThreadCpuTime（不需要 safepoint），补 spark 只采 Client thread 的盲区
  • glFinish 干预：可选接管每帧的 GL11.glFinish()，并用 /fs glfinish on|off 游戏内秒切做 A/B
  • 崩溃感知：扫描 crash-reports，解析崩溃栈并归因（报告页「崩溃」区块）；JVM 退出钩子留下死前时间线
  • GC 关联：每次停顿自动标注是不是 GC（gc= 标注 + 聊天 [GC] + 报告页明细）
  • fps 骤降检测：滑动窗口，均值掉到一半以下提示
  • 世界上下文：停顿行附带维度/坐标（尽力而为，失败静默）
  • ini 热重载：改 framespike.ini 约 2.5 秒后生效，不用重启

HTML 分析报告

/fs report 生成的报告是单文件、数据内嵌的，双击就能看，不需要联网也不需要服务器。 /fs stop 会自动出一份（autoReport=true）。

区块内容
KPI停顿次数（可测条数）、累计时长、最长一次、平均 fps / tps
时长分档<100 / 100-199 / 200-499 / ≥500ms 四档 —— 这才是「难受程度」
原因归因按栈顶归类，宽度 = 累计时长
火焰图层数 = 调用深度，宽度 = 累计停留时长；点一下聚焦某一支，Esc 回退
CPU / 帧率每 60 秒一次采样的趋势线（fps / tps / 整机 CPU%）
崩溃从 crash-reports 解析：时间 / 异常 / 归因 / 报告文件（没有崩溃时隐藏）
对比选第二份日志，指标 / 分档 / 归因逐项对比，变差红、变好绿
停顿明细时刻、真实时长、原因（GC 标注）、卡在哪一步、帧内时间线；点「栈」展开完整调用栈

字体默认就是圆体：圆体拉丁（Nunito / Quicksand / Varela Round）→ 圆体中文 （MiSans / HarmonyOS Sans / OPPO Sans / 阿里巴巴普惠体 / 思源黑体）→ 系统兜底， 装了哪个用哪个；调用栈和代码块仍保持等宽，不会因为「圆」而看不出缩进。

不开游戏出报告

java -cp out/main;resources;out/test ReportGen "<日志路径>" ["<输出目录>"]

报告只带最长的 400 条、每条栈最多 24 层（否则几百 KB 会变几 MB）。 没有真实时长（旧格式、无 STALL-END）的记录会标成「旧格式」并加 ~，不参与统计 —— 它们的时长只能等于阈值，混进来会把最长/分档带偏。

STALL-DETECT 是检测瞬间（只能知道「至少 60ms」），STALL-END 才是真实时长 —— 两者必须分开，否则一次 1.6s 的冻结会被记成 60ms。

为什么两套名字都写：1.8.9 运行时 MC 类的成员名是 notch 混淆名（av()V）， 不是 spark 栈里显示的 func_71411_J —— 那是 spark 自己反混淆后的显示名。 按 SRG 名写 hook 会全部 0 命中且没有任何报错。所以两列都匹配，并把命中项打进日志。

已知限制

  • 只采客户端线程：后台线程的栈看不到（有 CPU 表兜底）。要全采得改 thread_dumper 配置。
  • 采样间隔 2ms，加上 Windows 定时器粒度约 15.6ms，所以 50ms 级别的小抖动只能给出近似值；≥200ms 的停顿检出很可靠。
  • 单次冻结无法定位到「具体某一行」以外的东西 —— 只能给栈顶若干帧。
  • glFinishMode=proxy 需要重启一次才生效（-XX:+DisableAttachMechanism 封了 retransform）。

踩过的坑

这四条都是「静默失效」型，最难查。

notch 名字不是 SRG 名

1.8.9 运行时 MC 类的成员名是 notch 混淆名（av()V）， 不是 spark 栈里显示的 func_71411_J —— 那是 spark 自己反混淆后的显示名。 按它写 hook 会全 0 命中，而且一句报错都没有。

参数被砍了一截

vanilla 的 executeCommand 会先 dropFirstString：/fs start 到手是 ["start"]。 按 ["fs","start"] 写就会读不到，每个子命令都掉进「未知」。两种约定都要归一化。

检测时刻 ≠ 时长

阈值型看门狗如果「一越过就记录」，记到的是阈值本身： 一次 1589ms 会被记成 60ms，分档/最长/累计全废。必须等下一次推进再结算。

游戏开着换 jar

运行中的 jar 被 JVM 锁住，旧版挪不走。此时绝不能只装新版—— 两个 coremod 会被同时加载 = 双份字节码注入。装机脚本会先做占用检测并拒绝。
